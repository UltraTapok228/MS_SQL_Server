Разбор основных механизмов транзакций в MS SQL Server: базовые команды, уровни изоляции, вложенные транзакции, SAVE TRAN, обработка ошибок и управление журналом транзакций.

## Задание 1. Базовые команды управления транзакциями и уровни изоляции

 
### Что требовалось
Изучить команды управления транзакциями (BEGIN TRANSACTION, COMMIT, ROLLBACK, неявные транзакции) и уровни изоляции транзакций.

### Что сделано
Рассмотрены базовые команды и установка уровня изоляции:

```sql
BEGIN TRANSACTION; -- Начало
COMMIT; -- Успешная фиксация (изменения становятся постоянными)
ROLLBACK; -- Откат (отмена всех изменений)
SET IMPLICIT_TRANSACTIONS ON; -- Включение неявных транзакций
```

```sql
SET TRANSACTION ISOLATION LEVEL 
    { READ UNCOMMITTED | READ COMMITTED | REPEATABLE READ | SNAPSHOT | SERIALIZABLE };
```

### Анализ
- Транзакция — логическая единица работы, переводящая базу данных из одного согласованного состояния в другое.
- По умолчанию в SQL Server работает автофиксация: каждая инструкция фиксируется сразу после завершения.
- При IMPLICIT_TRANSACTIONS ON новая транзакция начинается неявно после завершения предыдущей, но требует явного COMMIT или ROLLBACK.

| Уровень | Поведение |
|---|---|
| READ UNCOMMITTED | Нет блокировок на чтение, возможны «грязные» данные |
| READ COMMITTED | По умолчанию, запрещает чтение грязных данных |
| REPEATABLE READ | S-блокировки до конца транзакции, но возможны фантомы |
| SERIALIZABLE | Наивысший уровень, блокирует весь диапазон ключей, нет фантомов |
| SNAPSHOT | Требует ALLOW_SNAPSHOT_ISOLATION ON, использует версии строк в tempdb вместо блокировок |

### Вывод
Уровень изоляции — компромисс между согласованностью данных и параллелизмом. SNAPSHOT снижает вероятность тупиков за счёт версионирования строк.

## Задание 2. Вложенные транзакции

 
### Что требовалось
Показать поведение вложенных транзакций: как COMMIT и ROLLBACK внутренней транзакции влияют на внешнюю.

### Что сделано
Создана таблица tbl. Во внешней транзакции вставляется test1, затем открывается внутренняя транзакция со вставкой test2. В зависимости от значения @i внутренняя транзакция фиксируется (COMMIT) или откатывается (ROLLBACK). После неё вставляется test3 и фиксируется внешняя транзакция.

```sql
CREATE TABLE tbl(id int identity,field varchar(50))
DECLARE @i bit
BEGIN TRAN
  INSERT tbl(field) SELECT 'test1'
  SELECT @i=1 --or 0
  BEGIN TRAN
    INSERT tbl(field) SELECT 'test2'
    IF @i=1 ROLLBACK TRAN ELSE COMMIT TRAN
  INSERT tbl(field) SELECT 'test3'
COMMIT TRAN
SELECT * FROM tbl
DROP TABLE tbl
```

### Результат (ожидаемое поведение)

| @i | Внутренняя транзакция | Итог |
|---|---|---|
| 0 | COMMIT | В таблице test1, test2, test3 |
| 1 | ROLLBACK | Откатилось всё, что было до ROLLBACK; test3 вставляется уже вне транзакции, финальный COMMIT выдаёт ошибку (нет активной транзакции) |

### Анализ
- COMMIT внутренней транзакции не освобождает ресурсы и не делает изменения постоянными — он лишь уменьшает @@TRANCOUNT на 1.
- Изменения фиксируются только при фиксации самой внешней транзакции (когда @@TRANCOUNT становится равным 0).
- ROLLBACK любой вложенной транзакции откатывает все внешние транзакции.

### Вывод
Вложенность транзакций в SQL Server условная: реальная фиксация происходит только на внешнем уровне, а откат всегда полный.

## Задание 3. Точки сохранения

 
### Что требовалось
Показать работу SAVE TRAN: частичный откат работы внутри транзакции до точки сохранения.

### Что сделано
Создана таблица ValueTable. Вставлены значения 1 и 2, установлена точка сохранения SavePoint1, затем вставлено значение 3 и выполнен откат к SavePoint1. После этого вставлено значение 4.

```sql
CREATE TABLE ValueTable ([value] int)
BEGIN TRAN
       INSERT INTO ValueTable VALUES(1)
BEGIN TRAN
       INSERT INTO ValueTable VALUES(2)
SAVE TRAN SavePoint1
BEGIN TRAN
       INSERT INTO ValueTable VALUES(3)
ROLLBACK TRAN SavePoint1
INSERT INTO ValueTable VALUES(4)
SELECT * FROM ValueTable
DROP TABLE ValueTable
```

### Результат (ожидаемое поведение)
SELECT возвращает значения 1, 2, 4. Значение 3 отменено откатом к точке сохранения.

### Анализ
- SAVE TRAN SavePoint1 устанавливает точку сохранения.
- ROLLBACK TRAN SavePoint1 отменяет только работу, выполненную после создания точки (вставку значения 3).
- В отличие от полного отката, откат к точке сохранения не уменьшает @@TRANCOUNT, транзакция остаётся активной.

### Вывод
SAVE TRAN позволяет откатывать часть работы, не отменяя всю транзакцию.

## Задание 4. Обработка ошибок

 
### Что требовалось
Показать обработку ошибок в транзакции с помощью TRY...CATCH и SET XACT_ABORT, а также проверку состояния транзакции через XACT_STATE().

### Что сделано
Создана таблица table1 с ограничениями NOT NULL и PRIMARY KEY. При SET XACT_ABORT ON в блоке TRY выполняются три вставки, причём вторая нарушает NOT NULL (col1 = NULL). При ошибке управление переходит в CATCH, где выполняется ROLLBACK. После блока проверен XACT_STATE().

```sql
CREATE TABLE table1 (i int NOT NULL PRIMARY KEY, col1 varchar(20) NOT NULL, col2 varchar(20) NULL);

SET XACT_ABORT ON; -- Управление откатом

BEGIN TRY
  BEGIN TRAN
  INSERT INTO table1 (i,col1,col2) VALUES (1,'First row','First row'); 
  -- Вставка с ошибкой (если есть нарушение ограничений)
  INSERT INTO table1 (i,col1,col2) VALUES (2,NULL,'Second row'); 
  INSERT INTO table1 (i,col1,col2) VALUES (3,'Third row','Third row'); 
  COMMIT TRAN; 
END TRY 
BEGIN CATCH 
  ROLLBACK TRAN; 
END CATCH;

SELECT XACT_STATE();
```

### Результат (ожидаемое поведение)
Вторая вставка вызывает ошибку, транзакция откатывается целиком, таблица остаётся пустой, XACT_STATE() возвращает 0.

### Анализ
- XACT_ABORT ON: любая ошибка обрывает транзакцию и выполняет полный откат. При OFF (по умолчанию) в некоторых случаях откатывается только ошибочная инструкция, а транзакция продолжается.
- TRY...CATCH перехватывает сбой и передаёт управление в CATCH, где можно безопасно вызвать ROLLBACK.
- XACT_STATE(): 1 — транзакция активна и может быть зафиксирована, 0 — активной транзакции нет, -1 — произошла ошибка, транзакция «мертва» и допускает только полный откат.

### Вывод
Связка TRY...CATCH + XACT_ABORT ON гарантирует атомарность: частично выполненная транзакция не останется в базе.

## Задание 5. Управление журналом транзакций

 
### Что требовалось
Разобраться, как освобождается место в журнале транзакций и как уменьшить физический размер файла журнала.

### Что сделано
Рассмотрена команда уменьшения файла:

```sql
DBCC SHRINKFILE (DataFile1, 7);
```

### Анализ
- Усечение (truncation) журнала происходит автоматически: виртуальные файлы журнала (VLF) помечаются как неактивные, освобождается место внутри файла, но физический размер файла на диске не уменьшается.
- Для реального уменьшения файла применяется DBCC SHRINKFILE: указывается логическое имя файла и желаемый размер в мегабайтах.

### Вывод
Усечение освобождает место внутри журнала, а DBCC SHRINKFILE — место на диске.
